# 编码手册：微服务 RCA 论文报告实践小调查

## 目的
本手册供两名独立编码人员使用，对 `papers.csv` 中列出的 2022–2026 年微服务根因分析（RCA）方法/基准论文，编码四项报告实践指标。编码人员之间不应讨论具体论文的判定，编码完成后计算 Cohen's kappa 衡量一致性。

## 选文规则（编码人员核对用，非编码人员自选论文）
- 年份：2022–2026（发表年或 arXiv 首次提交年，以较早者为准；少数早于该窗口但被广泛引用为基线的锚点论文（TraceRCA, IWQoS 2021；MicroRank, WWW 2021）例外收录，并在 `papers.csv` 的入选理由列注明"锚点、年份例外"）。
- 主题：微服务或云原生系统的 RCA / 故障定位方法论文，或 RCA 基准 / 评测论文。
- 必须在至少一个公开或自建基准上报告定量结果（准确率、Top-k、AC@k、精确率、召回率等）。
- 来源优先顶会顶刊（ICSE、FSE/ESEC、ASE、ISSTA、WWW、KDD、NeurIPS、ICML、ICLR、ISSRE、DSN、SoCC、IWQoS、TOSEM、TSE 等）与被广泛引用的 arXiv 预印本。
- 任一作者组（以通讯作者/实验室为准）在清单中出现不超过 5 篇。
- 每篇论文的入选理由分两类：「锚点」（任务书列名的必收录论文）或「检索」（通过关键词检索命中，检索式记录在 `papers.csv` 的检索式列）。

## 编码总体流程
1. 阅读全文（`texts/<id>.txt`；缺全文的论文见 `papers.csv` 备注，只能依据摘要/可获得部分编码，编码人员必须在 `note` 列写明"仅摘要/部分文本"）。
2. 对每篇论文、每个编码项，独立填写一行到编码 CSV。
3. 每项证据必须能在原文中定位到具体章节号、表号或页码；找不到明确证据时不得编造。

## 编码输出格式
编码人员各自产出一个 CSV，列如下：

| 列名 | 说明 |
|---|---|
| `id` | 对应 `papers.csv` 的论文 id |
| `item` | `Q1` / `Q2` / `Q3` / `Q4` 之一 |
| `value` | 见各项取值定义 |
| `evidence_quote` | 逐字摘录支持该判定的原文片段，不超过 60 词；`value` 为 `no` 或 `not_applicable` 且无可摘录证据时留空，但需在 `note` 说明判定依据（例如"通读全文未发现相关段落"） |
| `location` | 证据在原文中的位置，如"§5.2""Table 3""p.7" |
| `note` | 补充说明：边界情况、判定的犹豫点、是否只有部分文本等 |

每篇论文每项恰好一行，四项共四行。

## Q1：是否报告逐系统（per-system）结果

**定义**：论文的实验部分是否对每一个被测系统/数据集（例如 Sock Shop、Online Boutique、Train Ticket、或基准中的不同子系统/子数据集）分别报告了性能数字（而不仅仅是跨系统合并或平均后的单一数字）。这里的"系统"指论文自己划分的评测单元——通常是一个独立部署的微服务应用或一个独立的数据集分片；如果论文只用了一个系统，本项记为 `not_applicable`。

**取值**：
- `yes`：对每个系统都单独列出了至少一个性能指标（表格分系统列、或正文分系统讨论均可）。
- `partial`：只对部分系统分别报告（例如 3 个系统中只单独报告了 2 个，第 3 个只出现在合并数字里），或者分系统数字只出现在附录/补充材料而正文只有合并数字。
- `no`：论文使用了多个系统，但所有报告的数字都是跨系统合并或平均后的单一数字，找不到任何分系统拆分。
- `not_applicable`：论文自始至终只在一个系统/一个数据集上做实验。

**判定规则**：
- 只要能在正文或附录任何位置找到分系统的数字（哪怕只是一个脚注或补充表），且覆盖全部系统，记 `yes`。
- 消融实验（ablation）里出现的分系统结果也算数，不要求必须出现在主表。
- 如果论文报告了"平均 Top-1"和"各系统 Top-1"两种数字，只要后者存在就不算合并掩盖，记 `yes`（即使主表标题突出的是平均数）。

**正例（自拟示例，非清单中论文原文）**："Table 3 reports Top-1 accuracy separately for System A, System B, and System C, in addition to the mean in the last column。" → `yes`。

**反例（自拟示例）**："我们的方法在所有数据集上的平均 Top-3 准确率为 0.82，超过所有基线。"（全文只出现这一句合并数字，不存在任何按系统列出的表格）→ `no`。

**边界情况**：
- 论文报告了"每种故障类型"的拆分，但没有"每个系统"的拆分——如果故障类型与系统一一对应（例如某故障类型只在某系统里出现），可视为等价于分系统拆分，记 `yes` 并在 `note` 说明"按故障类型拆分等价于按系统拆分"；如果故障类型跨系统共享，则不等价，仍记 `no`/`partial`。
- 只报告了案例数（case count）而非性能指标的分系统统计，不算数（这是描述数据集，不是报告结果），仍按实际性能数字判定。

## Q2：是否公开逐案例（per-case / per-fault-instance）输出

**定义**：论文或其配套代码仓库/补充材料是否公开了逐个故障案例（每一次故障注入或每一个真实故障实例）的方法输出或预测结果（例如每个案例的 Top-k 候选根因列表、每个案例的预测正确与否），而不仅仅是聚合后的统计量。

**取值**：
- `yes`：论文正文/附录/代码仓库/artifact 中能找到逐案例级别的输出或预测记录（哪怕只是一个 CSV/JSON 文件列出每个案例的预测）。
- `partial`：公开了逐案例的输入数据或故障标签，但没有公开逐案例的方法输出/预测（只能自己复现后才能拿到逐案例结果）；或者只对部分方法/部分系统公开了逐案例输出。
- `no`：完全没有逐案例层面的公开材料，只有汇总指标。
- `not_applicable`：论文没有可下载的代码/数据/附录（例如工业界闭门报告、只有 PPT），无法评估是否可能公开。

**判定规则**：
- 检查论文中是否提到"case study""per-case results""raw outputs""released predictions"等字样，并检查论文中提供的代码仓库链接（如果链接在全文中出现，可根据论文文字描述判定，而非要求编码人员真的去克隆仓库跑一遍；如果论文正文明确说"we release per-case results at <链接>"，记 `yes` 并在 `evidence_quote` 摘录该句）。
- 如果论文只是提到"代码开源"但没有明确说输出/结果也开源，且编码人员未去核实仓库内容，记 `partial` 并在 `note` 注明"代码开源但未核实是否含逐案例输出"。
- 案例研究（qualitative case study，仅描述 1-2 个案例作为示例）不构成"公开逐案例输出"，因为它不覆盖全部案例。

**正例（自拟）**："We release the full set of per-incident root-cause rankings produced by each baseline at https://github.com/xxx/results, covering all 770 injected faults." → `yes`。

**反例（自拟）**："我们的方法在 770 个故障案例上的平均 Top-1 准确率为 0.65。"（全文和仓库都只字未提逐案例输出）→ `no`。

**边界情况**：
- 只公开了「案例的输入遥测数据」而非「方法的预测输出」，记 `partial`（因为输入数据可以让第三方自己跑，但不是作者自己方法输出的逐案例记录）。
- 复现包（reproducibility package）里包含运行脚本、但没有预先算好的逐案例结果文件，也记 `partial`。

## Q3：是否从合并/平均数字作出跨系统优越性表述

**定义**：论文是否存在这样的论证结构——仅依据跨系统合并或平均后的单一数字（而不是对每个系统分别比较），就得出"本方法全面优于/全面超过所有基线"一类的跨系统优越性结论。这是本调查最核心的一项，要求逐字摘录原文，不允许转述。

**取值**：
- `yes`：能在文中逐字摘录到至少一句这样的表述，且核实其唯一支撑证据是合并/平均数字（即：作者没有在同一处或附近同时给出分系统证据来支撑该表述）。
- `partial`：文中有类似的优越性表述，但表述本身有限定语（如"在我们评测的场景中平均而言""在多数系统上"），使其不构成无限定的"全面优于"断言；或表述同时援引了分系统证据（即使证据不完整）。
- `no`：文中没有发现任何这类跨系统优越性表述（可能全文只在单系统层面比较，或表述都紧扣具体系统）。
- `not_applicable`：论文本身不是方法论文而是纯基准/数据集论文，不存在"本方法优于基线"这种论证结构。

**判定规则**：
- 只统计摘要（abstract）、引言（introduction）、结论（conclusion）三处最常见的位置，但不限于此——只要找到就记录，位置写清楚。
- 摘录必须逐字，不超过 60 词；如果原句更长，摘录包含"优越性断言"核心的完整从句即可，允许用省略号标记截断位置。
- 判断"唯一支撑证据是合并数字"时，只看该断言所在段落及紧邻的前后两段是否引用了分系统数字；如果分系统数字出现在同一表格但断言本身没有引用它（例如断言引用的是表格最后一列"Average"），仍记 `yes`。
- 常见的合并优越性表述模式："our method outperforms/surpasses all baselines""achieves the best/state-of-the-art performance across all systems/datasets""consistently outperforms"——出现这类模式且后面没有例外限定（如"except for System X"）时，优先怀疑为 `yes`，再回头核实证据来源。

**正例（自拟）**："Averaged across the three benchmark systems, our approach achieves a Top-1 accuracy of 0.71, outperforming all seven baselines。"（结论段落，无分系统限定，无例外说明）→ `yes`，摘录该句。

**反例（自拟）**："在 Sock Shop 上我们的方法 Top-1 达到 0.80，在 Train Ticket 上为 0.55，略低于 CIRCA 的 0.58；总体来看我们在两个系统里各有优势。"（明确逐系统比较，未做无限定的整体优越性断言）→ `no`。

**边界情况**：
- "在我们测试的 5 个基线中有 4 个上表现更好"这种带具体计数的表述，不算无限定断言，记 `partial`。
- 优越性断言出现在相关工作对比表的表头文字（如表格标题写"Our method achieves SOTA"）而非正文叙述，仍然算数，摘录表格标题。
- 如果论文对"优于所有基线"做了统计显著性检验（如报告 p 值或置信区间）覆盖所有系统，则不算本项要捕捉的问题模式，记 `no` 并在 `note` 说明"有统计检验支撑，不构成本项定义的问题模式"。

## Q4：是否记录输入表示/预处理版本

**定义**：论文是否清楚说明了实验所用输入数据的具体版本、文件或预处理步骤——例如：用的是原始导出表还是精简/聚合后的表、用了哪些具体的指标列、做了何种归一化/重采样/缺失值处理、以及所用基准代码或数据的版本号/commit/日期。这一项关注可复现性中最容易被忽略的"数据版本"细节，而不是"数据集叫什么名字"这种粗粒度信息。

**取值**：
- `yes`：论文明确写出了输入文件/表示的具体版本或预处理细节，使读者能够分辨这是原始表还是精简表、用了哪些列、做了什么变换。
- `partial`：提到了"我们做了预处理"或"我们使用了某基准的数据"，但没有说清楚具体版本/文件名/列集合/commit 号，读者无法据此复现相同输入。
- `no`：完全没有提及输入数据版本或预处理相关信息，只说了数据集名称和规模。
- `not_applicable`：论文本身不使用任何需要版本区分的公开基准数据（例如所有实验数据都是作者自建的一次性内部数据，不存在"版本"概念）。

**判定规则**：
- 检查方法部分（通常是"Experimental Setup" / "Datasets" 小节）和附录，寻找诸如"we use the `simple_metrics.csv` file""we select 51 out of 438 columns""commit hash / version tag / release date"等具体细节。
- 只说"我们使用 RCAEval 提供的三个数据集"而不说明具体读取的是哪个文件、哪些列，记 `no` 或 `partial`（视是否有任何列名/文件名线索而定）。
- 代码仓库里的配置文件不计入判定依据，除非论文正文明确指向该配置作为可复现的版本说明。

**正例（自拟）**："We use the `simple_data.csv` file provided by the benchmark, which retains 60 of the original 438 metric columns after removing redundant per-container duplicates, collected at 1-minute resolution。" → `yes`。

**反例（自拟）**："我们在 Sock Shop 和 Train Ticket 数据集上进行了评测。"（全文再无关于具体文件、列数、预处理步骤的任何描述）→ `no`。

**边界情况**：
- 只在图表标题里写了列数（如"51 metrics"）但正文完全没有解释这 51 个指标是如何从原始数据筛出的,记 `partial`。
- 论文引用了别的论文的预处理流程（"we follow the preprocessing in [X]"）且给出了具体引用，视为记录了版本/流程,记 `yes`，并在 `note` 注明"通过引用间接说明"。

## 通用注意事项
- 四项编码互相独立，不因为 Q1 判 `no` 就默认 Q3 判 `yes`；每项都要单独在原文中核实。
- 遇到论文有多个版本（如 arXiv 预印本与正式会议版本内容不一致）时，以 `papers.csv` 中记录的 `fulltext_file` 对应版本为准，不混用其他版本的内容。
- 编码人员之间在正式提交前不得互相对照答案；所有分歧留到计算 Cohen's kappa 之后由第三方（本项目负责人）裁决，不在编码阶段自行统一口径。
